# Coach workflow

The five chat starters cover a single-day workout log or plan, protein/creatine, supplements/sleep, exercise teaching and progress assessment. Multiweek routine building has been removed from the offered skills. The application resolves intent, retrieves context, interprets the request, validates the result, and either answers or shows a pending preview. The model has no journal-writing tool.

## Pending tasks and approval

The chat composer shows the logging date and explains that messages can override it. Clearing that date prompts the user to choose or state a date before a new logging request is sent; ordinary coaching questions and corrections to dated previews remain available. Typed ISO, day/month/year, named month dates, today and yesterday override the selector. Relative logging dates use the actual current day rather than shifting an older selected journal date again.

Meal previews offer **Adjust totals** beside the existing approval actions. Users can confirm protein and calorie totals and an optional protein range, then approve without model inference. Original per-food estimates remain unchanged; confirmed totals are explicitly marked and used for recorded intake. Batch adjustments target the selected meal's stable ID and preserve the other entries. Validation, stale-day protection and request replay still apply. Manual food forms also expose optional range fields, and ranges display and save to two decimal places. Blank calories remain optional for manual entries.

The activity calendar uses Clear & bright colors: below 50% red, 50–59% orange, 60–69% yellow, 70–79% light green, 80–89% medium green and 90%+ brightest green. Unlogged and future days remain neutral. Sleep calendar coverage is uncapped, including weekly averages; it still considers both total-rest and night-sleep goals. Consistency scoring retains its own caps.

Each batch entry has a stable `item_id`, retained through validation, restarts and correction proposals. Reordered corrections match these IDs before descriptive fields. Repeated activities and same-day home sessions remain separate; ambiguous corrections retain the pending preview and ask which session to change. Gym/home categories are validated inside batches as well as standalone previews. Explicit gym sessions remain gym sessions; home exercise approvals never merge into gym records. Mixed activity and intake requests bypass intake-only shortcuts.

`coach_workflow.py` patches the original workout source during clarifications. A persisted task stores the source, date, current draft ID, unresolved state and candidate choices. It survives server restarts independently of the short message window. Repeated equal sets remain separate; repeated exercise names append sets in source order. A correction regenerates the complete preview and dismisses its predecessor. Multiple exercise clarifications can be applied in the same correction. The broad logging selector cannot override a specific workout request, and starter wording is not treated as an exercise. Model-produced partial workout, meal or mixed-log replies are merged with untouched entries.

Ambiguous equipment and semantic-only matches require confirmation. The preview offers up to three real library names. A numbered choice works when a single movement is awaiting selection; users can also supply a name or clarification. Unknown movement quantities remain in the original source. Approving an incomplete workout is rejected by the store, including through the Track approval endpoint. Approval is disabled in the chat card until the questions are resolved.

Topic changes and a new chat dismiss the pending preview. No approved journal records are undone by cancellation. Meal approvals append a new meal; workout approvals retain the existing application's same-day merge rules and optimistic stale-day check. Plans remain exercise selections, separate from completed sets.

## Local retrieval and context

`semantic_index.py` stores exercise names, aliases, equipment, muscles and instructions, plus one dated chunk per journal entry, in `coach_chunks` in the journal SQLite database. Saving, editing or deleting an entry changes its retrieval chunk in the same transaction. Pending drafts never enter the journal evidence collection. Reset removes journal and conversation chunks. Background embeddings use the installed local `embeddinggemma:latest` model through Ollama. No embedding model is downloaded automatically.

Run `ollama pull embeddinggemma` once on a new installation. On startup the worker backfills missing embeddings in batches. Independent exercise queries are embedded in one batch; background indexing pauses during a coach turn. Search fuses local dense-vector cosine similarity with keyword overlap and checks that candidate movements match the requested anatomy/action. Keyword retrieval remains available while embeddings are unavailable or being built; returned evidence records which retrieval path was used. Query vectors are cached in a bounded process-local cache. Document text is retained in full; embedding input is bounded for the small model's context window. A digest check prevents a concurrent edit or deletion from being overwritten by stale background vectors.

Short-term context contains at most three recent user-led exchanges under a token budget. Longer conversations retain quoted user/coach exchanges in a separate retrieval collection; quotes are explicitly unverified conversation, not approved journal facts or instructions. Starting a new chat clears this recall collection and the task/scope state, while archived messages and approved journal entries remain in their existing stores. Profile goals and approved historical journal chunks supply durable context.

Assessment opens by asking how to begin. A “yes” continues the assessment, covering workouts and intake/recovery. Explicit date ranges, days, weeks, categories and subsequent focused follow-ups set a persisted scope. SQL metadata filters run before semantic ranking. Application-computed metrics use the full filtered record set; a top-k retrieval sample cannot establish totals or missing-day intake. The application prints computed observations, goal references and comparable first/latest exercise sets; Qwen supplies bounded next-step suggestions. It discards numeric or goal-attainment assertions in those suggestions. This prevents model-generated claims such as 30 g meeting a 120 g goal from becoming the assessment. Missing logs remain distinct from actual zero intake.

## Response budget and formatting

Scoped assessments include moderate and high-intensity cardio minutes, moderate-equivalent minutes, known calories and counts of meals with unknown calories. Missing calorie values make the reported total incomplete. Activity scope detection and chat routing share the complete cardio catalog and aliases, so mixed sport/sleep reviews retain both categories. Local assessment schemas request suggestions only for the selected categories, including home training.

The chat endpoint accepts `stream:true` and returns newline-delimited stage, final or error events. The browser displays stages immediately; it displays the final answer and actionable draft after validation. Raw model JSON and internal deliberation are not streamed into the conversation. Request IDs retain replay protection, and non-streaming clients remain supported.

Normal coaching uses one Qwen generation. Explicit workout notes and configured intake shorthand can complete through extraction, retrieval and validation without generative copying. Input is scoped rather than sending the exercise library or full journal to Qwen. Generation uses structured JSON, low temperature, a warm model, bounded output and a 30-second response target rather than a failure cutoff; separate unrestricted thinking output is disabled. Public research and tutorial waits are bounded. Slow local inference streams transport progress every three seconds and can continue beyond the target (up to 120 seconds per model step and 180 seconds of turn work). Actual useful-answer latency depends on hardware and model loading. A model/transport failure returns a recoverable assistant turn with any pending preview retained; it does not mark the supplied message as a failed workout or save a journal entry. Failed requests can be resumed with their original ID without duplicating the user turn.

Lessons require steps, form cues and common mistakes. The exercise library supplies source instructions if a model reply is only an introduction. Public DDGS video metadata search prefers a 30–60 second YouTube result. Duration is metadata, not a claim that the video was watched. If a direct result cannot be retrieved, the answer supplies a public YouTube search link. There are no embedded players, account connections or API keys.

## Validation

Tests use disposable journals. `tests/fixtures/workout_revision.txt` reproduces the reported nine-line note: after the leg raise and curl equipment are clarified, the approved workout contains eight distinct movements and all 23 sets, including six cable-row sets and plank durations of 60 and 40 seconds. Regression coverage also includes topic cancellation, stale approvals, optional sleep details, supplement goal units, semantic retrieval, transactional index updates and streamed UI parsing.
